# PM 决策表

## D-001: SubTask 模型裁决

状态：已裁决

结论：

1. `SubTask` 独立建模。
2. MVP 中，长期任务每日拆解项不用 `SubTask` 表示，而是用普通 `Task` 表示，并通过 `parentLongTermTaskId` 关联长期任务。
3. 普通任务下的 checklist 子项才使用 `SubTask`。
4. 普通任务下的 `SubTask` 属 P1；即使后续支持单独勾选，默认也不产生 XP。

产品原因：

长期任务每日拆解项是用户当天真正要完成的任务，应该进入今日列表、触发完成反馈链、参与 XP 和长期任务进度。普通任务 checklist 只是任务内部拆分，如果每个 checklist 都产 XP，会制造刷经验空间，违背“成长必须真实”。

契约影响：

`Task` 需要预留 `parentLongTermTaskId` 与 `rewardEligible` 字段。长期任务每日项满足 `rewardEligible = true`。普通 `SubTask` 默认 `rewardEligible = false`。

## D-002: 长期任务完成与取消裁决

状态：已裁决

结论：

1. 能够被一次性直接完成的事项不应建模为长期任务。
2. 长期任务必须有时间范围，至少跨越一天；如果没有跨天范围，应创建为普通任务。
3. 长期任务本体不允许被直接“完成”。
4. 长期任务只能通过其拆解出的 `Task` 进度汇总达成。
5. 普通任务和长期任务都允许被直接取消 / 放下。
6. 取消 / 放下不是完成，不触发 XP，不触发长期任务达成奖励，不计入负面统计。

产品原因：

长期任务的核心价值是把跨天目标拆成每日可执行的小任务。如果长期任务本体可以直接完成，它就退化成普通任务，也会绕过“真实持续完成”的成长逻辑。

契约影响：

长期任务需要 `startDate`、`dueDate`、`status`。`dueDate` 必须晚于 `startDate`。长期任务状态至少包含 `active`、`achieved`、`cancelled`。`achieved` 只能由子任务进度汇总触发；`cancelled` 由用户主动取消 / 放下触发。

## D-003: task_restored 事件裁决

状态：已裁决

结论：

补充 `task_restored` 事件，用于任务删除 / 放下后的撤销恢复、未来回收站恢复、同步 tombstone 恢复。

契约影响：

`task_restored` 不代表完成任务，不产生 XP，不触发怪兽投喂。它只表达“任务从删除态恢复为可见任务”。

## D-004: 今日任务激励裁决

状态：已裁决

结论：

1. 废弃“今日通关 / daily_clear”作为 MVP 核心概念。
2. 不再以“当日任务数 >=3 且全部完成”触发今日通关。
3. 改为“今日任务激励”机制：当日完成任务数达到 3 次时提示“小试身手”，达到 6 次时提示“收获满满”。
4. 第二天用户打开 App 时，对前一天任务完成情况进行正向反馈。
5. 累计完成超过 3 天时，给予累计经验奖励；MVP v0.1 暂定第 4 个活跃日一次性 +20 XP，计入每日正式 XP 上限，后续按数据调参。

产品原因：

“今日通关”会暗含必须清空任务列表的压力，也会在用户当天新增任务时制造奖励回滚问题。改成“今日任务激励”后，用户完成越多，正反馈越多，但不会因为没有清空清单而产生挫败感。

契约影响：

`daily_clear` 不进入正式契约。后续由契约组命名新的事件，例如 `daily_task_milestone`、`daily_task_summary`、`cumulative_active_reward`。

## D-005: 桌宠开关事件裁决

状态：已裁决

结论：

桌宠状态只保留打开和关闭两种。正式事件使用：

1. `desktop_pet_on`
2. `desktop_pet_off`

不设 `desktop_pet_toggle`，也不在 MVP 中拆出 show / hide / mute / unmute 等额外状态。

## D-006: Streak 与 streak_break 裁决

状态：已裁决

结论：

1. `Streak` 是连续完成任务的天数，目的是帮助用户养成好习惯。
2. 补充 `streak_break` 内部事件，用于记录连续天数中断。
3. `streak_break` 不得形成用户惩罚，不得触发羞辱、责怪、扣经验、怪兽负面状态。

## D-007: 无日期任务归属裁决

结论：

无日期任务默认归属“今天”。

产品原因：

MVP 优先降低记录成本，让用户快速进入“记录 -> 完成 -> 正反馈”的主循环。

## D-008: 取消今日通关回滚问题裁决

## D-017: Android Widget 技术路线裁决

状态：已裁决

结论：

Android Widget 技术路线优先采用 Glance。

产品与工程原因：

MVP 小组件只展示怪兽状态帧、今日进度、Streak / 今日任务激励状态，并支持点击回到 App，不做连续动画，也不做组件内直接勾选任务。Glance 更适合快速实现这种状态型 Widget。若后续遇到系统兼容、样式表达或性能限制，再局部退回 RemoteViews。

契约影响：

小组件仍只读取统一 `CompanionSnapshot`，不直接计算任务、XP、Streak 或怪兽状态。Glance 只是 Android Widget 的实现路线，不改变业务契约。

## D-018: 长期任务取消后的拆解任务处理

状态：已裁决

结论：

长期任务取消 / 放下时，未完成的每日拆解 `Task` 默认同步取消；已完成的拆解 `Task` 保留历史完成记录，不回滚已发生的真实完成行为。

## D-019: 无压清理动作语义

状态：已裁决

结论：

无压清理中的“放下”使用 `task_cancelled`；真正删除才使用 `task_deleted`。批量操作使用 `batch_cleanup_applied` 作为摘要，同时逐任务产生对应明细事件。

## D-020: 重复任务 MVP 边界

状态：已裁决

结论：

重复任务不进入 P0 正式实现，只保留 `repeatRuleId` 字段占位。复杂重复任务、多端确定性 occurrence 生成和冲突合并进入 P1。

## D-021: XpLedger 契约补充

状态：已裁决

结论：

`XpLedger` 进入节点 2 工程契约，作为 XP 的唯一账本来源。XP 只追加，不删除原记录；撤销通过负数 `xp_reverted` 冲正。

Widget 怪兽状态帧点击进入怪兽页；今日进度、今日任务激励、前日反馈、过期态点击进入今日页并触发刷新。不新增 Widget 点击埋点，P0 只保留 `widget_added`。

## D-023: 前日反馈生成时机

状态：已裁决

结论：

`daily_task_summary` 在第二天用户首次打开 App 时生成并展示，不做后台跨日预生成。

## D-024: 远端同步回放对 XP / Streak 的影响

状态：已裁决

结论：

远端 `completionSource = sync_replay` 允许触发本地 XP / Streak / Monster 重算，但必须使用原始 `eventId` / `sourceEventId` 幂等去重，不得重复发 XP。

## D-025: 睡眠唤醒保持时长

结论：

睡眠期间第 3 次抚摸触发 `wake_up`。若仍处于睡眠时间段，P0 让醒来状态保持当前前台会话内最多 10 分钟；之后若无继续互动，回到 `sleeping`。

## D-026: 等级回退表现

状态：已裁决

结论：

XP 撤销导致等级数据回退时，数据层立即校正；UI 只做静默刷新，不展示降级动画、惩罚文案或怪兽负面反馈。

## D-027: 注销冷静期内能力

状态：已裁决

结论：

`deletion_pending` 冷静期内默认只读；用户可以取消注销并恢复 `active`。除取消注销外，不允许新增会被同步的新任务、XP 或账号数据。

## D-028: “今晚”稍后提醒时间锚点

状态：已裁决

结论：

“今晚”P0 锚点为用户本地当天 `20:00`。若选择时已过 `20:00`，使用 `now + 1 hour`，但不得晚于勿扰开始；若会落入勿扰，则顺延到勿扰结束后的第一个可提醒时间。

## D-029: 完成与取消并发冲突

状态：已裁决

结论：

已完成任务不能直接取消；必须先撤销完成，再取消 / 放下。多端并发时，取消操作若基于旧 `active` 版本提交，应触发同步冲突重放，不得覆盖已完成事实。

## D-030: missing 状态阈值

状态：已裁决

结论：

P0 中，用户连续 3 个完整本地自然日未前台打开 App，下一次打开时可触发一次 `missing` 久别回归状态。

## D-031: 今日任务激励重复展示

同一用户、同一本地日、同一 `milestoneKey` 最多主动展示一次。撤销后再次跨过 3 / 6 阈值时，不重复弹出同一提示，但 Snapshot 可恢复显示当前达成状态。

## D-032: 前日 0 完成反馈

前日可奖励完成数为 0 时，不弹出前日反馈弹层；今日页可展示温和的被动鼓励卡，不使用断签、失败或责备文案。

## D-033: 批量无压清理撤销

状态：已裁决

结论：

P0 支持最近一次批量无压清理的短时整批撤销，恢复通过逐任务 `task_restored` / `task_rescheduled` 回放实现；完整回收站进入 P1。

## D-034: 多奖励展示顺序

勿扰期间桌宠保持可见但低动效，不弹提醒气泡、不播放声音、不使用吸引注意的强反馈；不引入 hide 状态。

## D-044: 节点 6 Android Widget 首轮技术边界

Android Widget 首轮优先采用 Glance 原生壳，但若当前 Flutter Android 工程模板或本机 Gradle 环境不适合一次接入完整 Glance，可先落地等价的原生 Widget 壳和配置占位。无论采用 Glance 还是占位壳，Widget 必须只读取持久化 CompanionSnapshot，不提供组件内勾选任务，不产生任务完成、XP、Streak 或怪兽状态变更事件。
## D-045: 节点 7 package 测试运行器口径

状态：已裁决

结论：

## D-046: 四形态怪兽像素化首轮交付边界

状态：已裁决

结论：

首轮交付为一张四形态同画面的彩色像素概念图，用于确认角色辨识度与像素美术方向。必须保留米黄卷轴材质、深色缝线、绿色发光眼部、橙红徽章、绿色勾选符号及两种分支进化的关键轮廓；采用中等精细度像素表现与统一色板。首轮不拆分透明单体精灵、不制作动画、不接入应用代码，待视觉方向确认后再立独立资产生产任务。

## D-047: 像素化强度返工口径

状态：已裁决

结论：

用户裁决首版像素化程度不足。第二版只强化像素美术语言，不改变四形态数量、布局关系、关键人设与主配色。目标为可清楚辨认的较大方形像素簇、硬边阶梯轮廓、受限色板与少量分层明暗，避免“高清插画叠加像素描边”、细碎高频纹理和顺滑抗锯齿。

## D-048: 第三版粗像素强度口径

状态：已裁决

结论：

用户要求在第二版基础上继续提高像素化程度。第三版采用更粗且全画面统一的像素网格、约 16 至 20 色的受限色板和每种材质最多两级主要明暗；减少装饰性小纹理、渐变与阴影过渡。四形态、分支关系、关键轮廓和识别色必须保留，粗化后仍须可一一对应原设。

## D-049: 宠物蛋像素化交付口径

状态：已裁决

结论：

两组宠物蛋分别交付，不合并为一张：第一组保留三枚不同观察角度，第二组保留三枚同向发光状态。像素强度、网格尺度、受限色板、硬边接地影和纯暖白背景与怪兽 v3-r3 保持一致。必须保留象牙白蛋壳、石灰绿眼环与勾选、深蓝眼芯和缝线、米色斜带、橙红蜡封；发光组须保留绿色与黄色标记的亮度差异。

## D-050: 宠物蛋三视角新参考图修改口径

状态：已裁决

结论：

仅修改三视角宠物蛋资产，发光状态组保持不变。新版以用户最新参考图为造型事实源：左侧为较完整正面偏左视角，中间为明显侧后视角且眼环与蜡封仅部分可见，右侧为正面偏右视角；米色斜带上的浅色短横按新参考图保留。像素规格继续使用 192×108 逻辑网格、9 倍最近邻、无抖动受限色板与纯暖白背景。

## D-051: 中间宠物蛋一致性修订

状态：已裁决
